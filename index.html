One log · Declared state · Reads at a position

Derived state, declared once and kept by the log.

Nerva is a research database. Indexes, views, change feeds, history and conserved balances are declared, then maintained from one ordered, replicated log, and every answer names the op it reflects.

See the goals Read the tutorial

Status: toy / research. Consensus, storage and the simulator come from TigerBeetle; Nerva has no external correctness review yet. Do not put data in it that you cannot lose.

Design principles
No pipelines between your data and what is derived from it

    
Keeping caches, indexes, aggregates, sync feeds and audit history in step with source data usually takes CDC, queues, consumers and backfill scripts. Nerva's bet is that all of it can be a deterministic function of one log.

    

      
The log is the truth
One ordered, replicated log. Base rows and every derived structure are deterministic functions of it, so every replica holds the same state at every op.

      
Every read names its op
Writes return their op. Reads ask for "at least op M" or "as of op N", and an as_of answer never changes later.

      
Declared, not hand-built
Views, indexes and ledgers are declarations in the log, not code. The state machine keeps them exact inside every commit.

      
Verifiable answers
A view's answer carries a hash of its groups. Replicas agree on it, and nerva view recomputes it from the log, byte for byte.

      
Conservation in the cluster
A declared ledger's fields move only by balanced pairs, never below a floor, whoever sends the request. No client can create or destroy value.

      
Claims without locks
Optimistic transactions: a read at the version seen plus a write. Two claimants of one receipt, exactly one wins, under crashes and faults.

    

  


  

    
Architecture
What runs today, layer by layer

    
One binary, nerva: replicas (start), a JSON gateway (api) and an independent view recomputer (view). Nerva's own code is the state machine; everything under it is vendored from TigerBeetle.

    

      

        
nerva api
JSON over HTTP
Every core operation for any language: lookups, commits, feeds, history, layouts, ledgers, views, indexes and documents. Bounded: 16 connections, 4 MiB bodies.

        
nerva view
Independent check
Follows the change feed and recomputes any view at any op, with the same hash the replicas serve.

        
client.zig
Zig client
A blocking client over the cluster protocol, in src/nerva/client.zig.

      

      

        
commit core
Rows and transactions
80-byte rows versioned by op; reads at op_seen, puts, deletes and bounded adds; commit keys so a resend commits once.

        
records · indexes
Facts
448-byte records under 128-bit ids, written in the same transaction as rows; declared indexes find them by their fields.

        
views
Declared views
where, group_by, count, sum, min, max, maintained in every commit and read as of any op.

        
ledgers
Conserved fields
Up to 64 ledgers of 2 to 16 i64 fields, changed only by pairs of adds, never below a floor.

      

      
the log
One ordered, replicated, hash-chained log
Every write, every declaration and every read goes through it. History, change feeds and as-of reads are indexes on it; nothing is physically deleted.

      
vendored from TigerBeetle
Consensus, storage, IO and the simulator
Viewstamped Replication, the LSM forest on a checksummed block grid, io_uring IO and the VOPR deterministic simulator, copied from TigerBeetle at a pinned commit. Every local change to a vendored file is listed in UPSTREAM.md.

    

    

      
The life of a commit

        
    
          
  1. Send. A client sends one transaction: reads with the version it saw, puts, deletes and adds, optionally under a commit key.
    2. 
          
  2. Order. The primary assigns it the next op and a timestamp and replicates it; once a quorum holds it durably, it is committed.
    3. 
          
  3. Prefetch. Each replica loads every row, record, view group and index entry the transaction touches. All IO happens here.
    4. 
          
  4. Validate. A stale read is conflict, an add past a bound out_of_bounds, a lone add to a conserved field unpaired. On any failure, nothing applies.
    5. 
          
  5. Apply. Rows, records, indexes, views and the change feed change in the same op, identically on every replica, with no IO and no clock but the prepare timestamp.
    6. 
          
  6. Reply. The client gets the op. Any later read can ask for at least that op, or as of it.
    7. 
        

      

      
How it is checked

        
    
          
  1. The VOPR. A whole cluster in one deterministic process, with crashes, partitions and disk faults; every reply is checked against a model, and every ledger's conservation after every commit. A seed replays a run exactly.
    2. 
          
  2. Seeded fuzzers. TigerBeetle's and Nerva's own: adds, HTTP heads, documents and more.
    3. 
          
  3. Against models. test:api and test:views check every route and every view against models, with write races.
    4. 
          
  4. Real clusters. Three real replicas, two releases in one cluster, upgrades by export and import, and the demos under random crashes.
    5. 
          
  5. Jepsen, by hand. Five nodes, kills, pauses and partitions; the history is checked for a ledger's conservation, so far.
    6. 
          
  6. Adversarial review. Before every release, a separate reviewer tries to break the candidate; each finding is a GitHub issue that blocks the release until fixed or waived.
    7.

Production
What stands between the engine and strangers' money

      
The engine already conserves balances and commits facts beside them. The R milestones are the work around it: proof under real faults, a fleet that never stops searching, the real topology measured, an honest gateway, recovery with the cluster open, rolling upgrades and bounded growth. Each ends in a demo that runs in CI; the gate for the first client's launch is R1 to R5. The plan →

    Limits and non-goals
    What Nerva is not, yet or ever
    
    
    Every limit a caller can hit is a constant in the code, asserted where it is used, and listed in the README.
    
    
    
      
    Status
      
        
    • Toy / research. No external correctness review comparable to TigerBeetle's Jepsen analysis yet.
      • 
        
    • The Jepsen suite exists, but runs by hand, and checks a ledger's conservation so far.
      • 
        
    • A release that changes the data file format needs new data files: upgrades go by export and import.
      • 
      
    
      
    Not for 1.0
      
        
    • SQL and general-purpose queries; PostgreSQL compatibility.
      • 
        
    • Object-storage tiering and external operators such as embeddings.
      • 
        
    • Application-specific protocols or routes: applications keep their own rules.
      • 
      
    
      
    Sizes
      
        
    • Rows hold 80 bytes, records 448, documents up to 512 KiB.
      • 
        
    • One op touches at most about 4,000 view groups; a larger transaction is refused whole.
      • 
        
    • A cluster holds 64 client sessions; at most 64 ledgers and 64 indexes.
      • 
      
    
      
    Network
      
        
    • Gateways speak plain HTTP with a shared key: put them behind TLS off a private network.
      • 
        
    • Replicas authenticate each other, but their traffic is not encrypted: run them on a private, encrypted network.
      •
